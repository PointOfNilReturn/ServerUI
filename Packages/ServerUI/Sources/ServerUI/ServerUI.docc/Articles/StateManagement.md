# State Management

Build reactive, stateful applications with server-side state management.

## Overview

ServerUI provides SwiftUI-like state management patterns that work seamlessly with server-driven UI. You can use `@State`, `@Binding`, `@RemotelyObservable`, and `@Bindable` just like in vanilla SwiftUI, while the framework handles synchronization with the client.

## @State

Use `@State` for simple value types that belong to a specific view:

```swift
struct CounterView: View {
    @State private var count = 0
    
    var body: some View {
        VStack {
            Text("Count: \(count)")
            Button("Increment") {
                count += 1
            }
        }
    }
}
```

### How It Works

1. **Server maintains state** in `StateStore` scoped to the view instance
2. **Client displays current value** from `ViewHierarchy.initialState`
3. **User interactions** send updates to server
4. **Server updates state** and re-renders view
5. **Client receives update** and refreshes UI

### View-Scoped Lifecycle

Each navigation to a view creates a new state instance. When the view is popped, its state is cleaned up:

```swift
// Navigate to counter → count = 0
// Increment to 5 → count = 5
// Pop back to previous screen
// Navigate to counter again → count = 0 (fresh state!)
```

## @Binding

Create two-way bindings to state for components like `TextField`:

```swift
struct UserForm: View {
    @State private var name = ""
    @State private var email = ""
    
    var body: some View {
        VStack {
            TextField("Name", text: $name)
            TextField("Email", text: $email)
            
            Text("Hello, \(name)!")
        }
    }
}
```

### Instant Updates on Client

The client uses a `ReactiveStateCache` that provides instant feedback as the user types, while debouncing updates to the server:

1. **User types "J"** → Client updates instantly (0ms)
2. **User types "o"** → Client updates instantly (0ms)
3. **User types "h"** → Client updates instantly (0ms)
4. **User types "n"** → Client updates instantly (0ms)
5. **After 300ms** → Client sends "John" to server
6. **Server updates @State** → Re-renders view
7. **Client receives update** → Confirms state

The user never sees lag - typing feels native!

## @RemotelyObservable

For complex objects with multiple properties, use `@RemotelyObservable`:

```swift
@RemotelyObservable
class UserProfile: @unchecked Sendable {
    var name: String = ""
    var email: String = ""
    var age: Int = 18
    var bio: String = ""
}
```

### Why the Macro?

The `@RemotelyObservable` macro generates the boilerplate needed for ServerUI to track and sync object properties:

```swift
// Generated by macro:
func _getObjectID() -> String { ... }
func _getProperties() -> [String: Any] { ... }
func _updateProperty(name: String, value: Any) { ... }
```

### Using Observable Objects

Declare observable objects with `@State`:

```swift
struct ProfileScreen: View {
    @State private var profile = UserProfile()
    
    var body: some View {
        ProfileForm(profile: profile)
    }
}
```

## @Bindable

Create bindings to individual properties of observable objects:

```swift
struct ProfileForm: View {
    @Bindable var profile: UserProfile
    
    var body: some View {
        VStack {
            TextField("Name", text: $profile.name)
            TextField("Email", text: $profile.email)
            TextField("Bio", text: $profile.bio)
            
            // Display current values (updates instantly!)
            Text(binding: $profile.name)
            Text(binding: $profile.email)
        }
    }
}
```

### When to Use @Bindable

- ✅ **Use @Bindable**: When you need to create bindings (`$profile.name`)
- ❌ **Don't use @Bindable**: When just reading values (read-only access)

```swift
// ✅ Good: Creating bindings
struct Editor: View {
    @Bindable var profile: UserProfile
    
    var body: some View {
        TextField("Name", text: $profile.name) // ← Needs binding
    }
}

// ✅ Good: Read-only access
struct Display: View {
    var profile: UserProfile // ← No @Bindable needed
    
    var body: some View {
        Text("Age: \(profile.age)") // ← Just reading
    }
}
```

## Text(binding:) for Instant Updates

For text that should update instantly as the user types, use `Text(binding:)`:

```swift
@Bindable var profile: UserProfile

VStack {
    TextField("Name", text: $profile.name)
    
    // ✅ Updates instantly as user types
    Text(binding: $profile.name)
    
    // ❌ Only updates after server response
    Text("Name: \(profile.name)")
}
```

### Why This Works

`Text(binding:)` creates a `.stateBound` spec that tells the client to read from the `ReactiveStateCache` instead of the static value. This provides instant updates without waiting for server round-trips.

## Button Actions

Buttons execute actions on the server:

```swift
Button("Reset") {
    profile.name = ""
    profile.email = ""
    profile.age = 18
}
```

1. **Client sends action** to server
2. **Server executes closure** (updates state)
3. **Server re-renders view** and sends to client
4. **Client updates UI** with new view

## Best Practices

### 1. Keep @State Private

State should be private to the view that owns it:

```swift
// ✅ Good
@State private var count = 0

// ❌ Avoid
@State var count = 0
```

### 2. Use Observable Objects for Complex State

For state with multiple related properties, use `@RemotelyObservable`:

```swift
// ✅ Good: Related properties in one object
@RemotelyObservable
class FormData: @unchecked Sendable {
    var firstName: String = ""
    var lastName: String = ""
    var email: String = ""
}

// ❌ Avoid: Multiple separate @State properties
@State private var firstName = ""
@State private var lastName = ""
@State private var email = ""
```

### 3. Pass Observable Objects Down the View Hierarchy

```swift
struct ParentView: View {
    @State private var profile = UserProfile()
    
    var body: some View {
        VStack {
            // Pass to children
            ProfileEditor(profile: profile)
            ProfileDisplay(profile: profile)
        }
    }
}

struct ProfileEditor: View {
    @Bindable var profile: UserProfile // ← Needs bindings
    
    var body: some View {
        TextField("Name", text: $profile.name)
    }
}

struct ProfileDisplay: View {
    var profile: UserProfile // ← Read-only
    
    var body: some View {
        Text(binding: $profile.name) // ← But still needs binding for instant updates!
    }
}
```

Wait - that won't work! You need `@Bindable` even for display if you want instant updates:

```swift
struct ProfileDisplay: View {
    @Bindable var profile: UserProfile // ← Need @Bindable for Text(binding:)
    
    var body: some View {
        Text(binding: $profile.name)
    }
}
```

### 4. Trust the Debouncing

Don't implement your own debouncing - `StateUpdater` handles it:

```swift
// ✅ Good: Just bind
TextField("Search", text: $searchQuery)

// ❌ Avoid: Manual debouncing
TextField("Search", text: $searchQuery)
    .onChange(of: searchQuery) { oldValue, newValue in
        // Don't do this - StateUpdater already debounces!
        debounceTimer?.invalidate()
        debounceTimer = Timer.scheduledTimer(...)
    }
```

## Under the Hood

### State Encoding

When encoding a view, ServerUI collects all current state:

```swift
// ViewHierarchy includes:
{
  "root": { ... view tree ... },
  "initialState": {
    "objectID::name": "John",
    "objectID::email": "john@example.com",
    "/path::state_File_42": "some value"
  }
}
```

### Client Synchronization

The client:
1. Initializes `ReactiveStateCache` from `initialState`
2. Binds all components to the cache
3. Sends updates to server with debouncing
4. Receives updated state and refreshes cache

### Race Condition Prevention

The cache tracks pending updates to prevent flashing:

```swift
// User types "ABC" → Cache marks as pending
// Server response for "ABC" arrives → Skipped (pending!)
// User deletes → Cache = "AB" (still pending)
// Server response for "AB" arrives → Confirmed, clears pending
```
